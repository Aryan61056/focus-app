## Matching-words rule (new, my decision, Settings switch "Count matching words as on task")
The model said "Not sure" for most real work windows, so a window whose title, page path or file path shares a distinctive word with the task or project description now counts as on task without asking the model (never on feeds, video or news sites; project allow/never rules and the never-judged list still win). On all three scenario sets it settles 33 of 62 on-task moments and waves through 2 of 45 off-task moments (both gray) and 0 of 40 unsure ones. It can only make Focus quieter, so it costs recall (a distraction sharing a word goes unnoticed), never a false nudge. These sets were also used to design it, so the numbers are a cost estimate, not held-out accuracy. It saves model calls too. With the real model, the developer-window sequence went from 1 of 9 reads "On task" to 7 of 9, and a video-site distraction still nudged at the expected time.

**Update:** the rule now also counts the app's name when the task names it ("notes in TextEdit"), except for browsers. Cost on the scenario sets: off-task waved through 3 of 45 (was 2): two Figma/Android Studio gray cases where the task names the app but the window is another project. ## Why clear distractions said "Not sure" (owner report 2026-10-02) and what changed
- **Cause (measured with the real model):** the first judge flagged the distraction correctly, but the second judge wrote a correct reason ("unrelated to the lab report") and then picked the category "supporting" for nearly every window, and the two-judge rule treated that as a veto. On 82 scenarios that reach the model in the app, recall on clear distractions was 47% (17 of 36).
- **Now:** (1) the second opinion is a plain question, "does this serve the task / unrelated / can't tell" (`core/prompts/instructions_v3.txt`); (2) the first judge must report confidence 95 or more before a window can count as off task (every off-task call that was really on-task work had 90 or less; the model says 95 when it is sure); (3) general-purpose apps (Finder, Terminal, Mail, Calendar, System Settings, Activity Monitor) are neutral, not judged, unless a project rule or the task names the app.
- **Result on a fresh set written before the change (39 scenarios, one run):** 11 of 15 off-task windows flagged, the other 4 stay "Not sure"; 0 of 12 on-task and 0 of 12 neutral windows flagged. On the older (spent) sets the same rule gave 88% recall with 0 on-task false flags, plus about 12 gray neutral windows (feeds, lofi video, LinkedIn) flagged, which are the cost. Small samples, one labeler; the thresholds were chosen on the older sets. Nudges still need sustained agreement in the brain, so one flagged window does nothing by itself.
- **New switch (Settings): "Judge with the on-device model"**, on by default. Off means rules and matching words only, everything else "not judged".
- **Wrong picture on Today:** the capture used the front app's biggest window, so a browser with several windows was read through another window (the words were from a different page). It now takes the topmost window of the app. Needs your Screen Recording grant to try for real.
- Tools: `FOCUS_PROBE=1 swift test --filter JudgeProbeTests` prints what each judge says about realistic windows; `FOCUS_LAB=1` compares second judges; `FOCUS_LAB_FINAL=scenarios_fresh2 swift test --filter JudgeLabTests/testShippedPipeline` runs the shipped pipeline on a set. `eval/scenarios_fresh2/` is the new set (spent after this run).

## Local auto-update (owner chose "local updates from this repo", 2026-10-13)
- **How:** `tools/build_app.sh` stamps every build with `FocusBuildID` (UTC timestamp, then git hash) and `FocusBuildSource` (the build folder). - **Verified:** 9 new tests (newer, same, older, unstamped, still-being-written, missing executable, never its own update, hidden during a session, Later, switch off); the helper script run for real on a scratch copy of the installed app (swapped to the new build, signature valid, reopened, no leftovers) and with a broken source (old copy kept and reopened).

## Tab switching, then closing on Strict (owner, 2026-10-13: "switches tabs first time and later on it closes it on strict mode")
- **What it does:** the first time the last step of the ladder runs on a browser (Safari, Chrome, Brave, Edge, Comet), Focus switches that browser to the tab you were last working in (the last window it read as on task). Later rounds hide the app as before, and on Strict they close the tab you were warned about instead. Two switches in Settings (both on): "Switch tabs first" and "Close the tab on Strict". The reminder banner says "Focus will close this tab next." before a close.
- **Limits by design:** only browser tabs Focus can name by address are closed; other apps are hidden, never quit (unsaved work). Private windows, sensitive pages and apps on the never-judged list are never closed. The tab is closed only if it is still at the page that was flagged. If a switch or close cannot be done (no earlier on-task tab, permission refused, browser slow), the app is hidden as before. Closing can lose unsaved work in that tab, which the setting says.
- **Permission:** macOS asks once per browser for Automation. Focus does not grant it; `NSAppleEventsUsageDescription` is in the app bundle.
- **Verified:** 285 tests: the choice rules, Standard (switch, then hide), Strict (switch, then close), each switch off, failed switch falls back to hiding, address escaping, and that the Safari scripts compile. **Not verified live:** the scripts running against a real Safari/Chrome (needs the Automation grant, which I cannot give), Chrome, Brave and Edge script details, a tab in a second window.

- **Chrome fix (owner, 2026-10-13: "the chrome version doesn't work"):** Chrome, Brave and Edge do not report the page address through Accessibility (Safari does), so Focus had no address for them: no tab to switch to, none to close, and every Chrome tab shared one "site" key, so the cover for one flagged tab covered all of Chrome. Now, while a session runs and a tab switch is on, Focus asks the browser for the front tab's address with AppleScript (same Automation permission; private windows return nothing; it stops asking for a minute if refused). The address goes to the judge as it already did for Safari.

## An explanation is not a free pass (owner, 2026-10-13: "make it so someone can't just say it's part of it and get away with it")
- **The hole I found:** an accepted explanation told the brain "that was fine", which saved an allow rule for the window key (host plus path, no query) in the project for good and in the session. So one accepted line about one YouTube video allowed every `/watch` page, in every later session. The friction cover also opened for the whole site for ten minutes.
- **Now:** an accepted explanation covers that one page (window key plus exact title, a leading "(3)" count ignored), only in this session, and nothing is learned or saved. The brain is told the page is on task by rule, the same path the matching-words rule uses, so the brain, its Rust port and the golden traces are untouched. The next video on the same site is a different page and is judged as before. The friction cover is skipped for that page only.
- **Shrinking and tightening:** each accepted explanation buys less (8, 5, 3, then 2 minutes) and needs a higher model confidence (80, 85, 90, then 95). A session allows 8, then the only way back is the task. When a pass runs out on the page you are on, Focus reads it again on its own, so it is flagged again if it is still off topic.
- **Pasted repeats:** an explanation that shares 60 percent or more of its content words with an earlier accepted one is refused without costing a try ("say what is in this window").
- **Other claims:** "That was fine" on a window Focus had not flagged also gets the same short page pass instead of a saved rule; it does not count toward the 8. Teaching Focus lasting rules is done in Projects, on purpose.
- **Ideas not built:** asking for a concrete deliverable and checking in when the pass ends; showing the accepted explanations in Review (the rule is counts only, never text); tying passes to the on-screen text when screen reading is on; making the model re-read the page mid-pass. Say which you want.
- **Verified:** 297 tests, including page-only coverage, expiry and re-flagging, shrinking passes and bars, pasted repeats and the cap. **Not verified:** how often Apple's real model refuses honest explanations at the higher bars (95 on the fourth).
